# PR 작업 절차

이 프로젝트의 변경 공유 경로는 **작업 브랜치 → 검증 → 커밋·push → PR → 검토·허용된 머지**다. `main`에 직접 push하거나 보호 규칙을 우회하지 않는다.

## 작업 준비

- 실제 Git 저장소 루트·원격·기본 브랜치와 작업 트리 상태를 확인한다. 기본 대상은 `main`이며 사용자가 지정한 대상 브랜치가 있으면 따른다.
- [루트 작업 규칙](../../../AGENTS.md)에 따라 계획·담당자 기록을 읽고 작업을 기록한다. 공통 절차 변경은 [PM 기록](../../../AGENTS/PM_progress.md)에 남긴다.
- 새 작업은 최신 대상 브랜치에서 `feat/`, `fix/`, `docs/` 등 작업 목적을 드러내는 별도 브랜치로 시작한다. 해당 작업 브랜치·PR이 이미 있으면 이어 쓴다.
- 미커밋 변경이 섞여 있으면 기존 작업을 보존하고 별도 worktree를 사용한다. 타인의 변경을 되돌리거나 다른 작업까지 한 PR에 묶지 않는다.

## 검증하고 PR로 공유

- 변경에 맞는 검사만 수행하고 명령·환경·실제 결과를 남긴다. 문서 변경은 링크/형식, 실행 코드 변경은 관련 동작/회귀를 확인한다. 실행하지 못한 검증과 실패는 그대로 명시한다.
- 실제 입력(`live`), 합성(`synthetic`), 녹화 재생(`replay`), 키보드 데모(`keyboard_demo`)의 검증 범위를 구별한다. 구현·자동 검사 통과만으로 실기기나 공통 Phase를 완료 처리하지 않는다.
- 이번 작업 파일만 선별해 stage하고 staged diff를 확인한다. 코드와 필요한 계획·계약·진행 기록을 함께 커밋하되 키·인증서·개인 설정·실험 데이터는 포함하지 않는다.
- GitHub 공유가 요청 범위에 포함되어 있으면 작업 브랜치를 push하고 PR 생성 또는 기존 PR 갱신까지 진행한다. 브랜치 push만으로 공유 완료라고 보고하지 않는다. 로컬 작업만 요청된 경우에는 로컬 변경과 게시 여부를 구별해 보고한다.
- [기존 PR 템플릿](../../../.github/pull_request_template.md)을 사용해 담당/Phase, 바뀌는 동작, 검증 명령·결과·입력 출처, 계약 영향·의존 브랜치, 남은 일을 적는다. 미완성 구현은 Draft로 공유한다. 실기기 확인만 남은 코드 PR은 그 한계를 명시하고 Phase 체크를 유지한다.
- 같은 작업 브랜치의 열린 PR을 먼저 확인해 중복 생성을 피한다. CLI로 여러 줄 본문을 전달할 때는 UTF-8 파일과 `--body-file`을 사용한다.

## 검토와 머지

- 머지는 현재 요청 또는 이어지는 대화에서 승인된 범위에서만 수행한다. 이미 받은 승인이 유효하면 같은 허락을 다시 요청하지 않는다. 새 PR 생성만으로 그 PR의 머지까지 승인됐다고 해석하지 않는다.
- 머지할 때는 최신 PR head·대상 브랜치·충돌·필수 검사·리뷰 상태를 확인한다. 검증 뒤 실행 코드나 의존 설정이 바뀌면 영향을 받는 검증을 다시 수행한다.
- 검증한 head SHA를 지정해 머지한다. 원격이 바뀌거나 검사/충돌로 머지가 거부되면 원인을 확인하고 해당 조건을 해결한 뒤 재검증한다. 강제 push·관리자 우회로 통과시키지 않는다.
- 실제 머지 결과와 대상 브랜치 반영을 확인한 뒤 PR 링크·커밋·검증 범위·남은 일을 보고하고 진행 기록을 갱신한다. 머지하지 않은 PR은 검토 대기로 표시한다.

이 스킬은 사람과 에이전트가 따르는 저장소 작업 절차다. GitHub의 브랜치 보호·권한 설정 변경은 별도 관리 작업이다.
