# 계획 읽기·진행 기록 운영 안내

**작업을 시작하기 전에 계획과 마지막 기록을 읽고, 끝날 때 다음 사람이 이어 할 수 있게 기록한다.** 루트 [AGENTS.md](../AGENTS.md)가 이 절차와 개인별 기록 파일을 안내한다.

## 1. 폴더 구성

| 파일 | 용도 | 갱신 주체 |
| --- | --- | --- |
| [진행현황.md](./진행현황.md) | PM이 보는 사람별 현재 작업·다음 작업과 공통 Phase 통과 현황 | 각 담당자 요약, PM 통합 결과 |
| [이동수_progress.md](./이동수_progress.md) | 화면·모델·게임 작업의 현재 상태와 누적 기록 | 이동수 또는 해당 작업 에이전트 |
| [김태이_progress.md](./김태이_progress.md) | 휴대폰·촬영·충돌·물리 작업의 현재 상태와 누적 기록 | 김태이 또는 해당 작업 에이전트 |
| [정경호_progress.md](./정경호_progress.md) | 서버·보정·3D·로그 작업의 현재 상태와 누적 기록 | 정경호 또는 해당 작업 에이전트 |
| [PM_progress.md](./PM_progress.md) | 공통 문서, 계획 변경, 결정, 통합 확인과 인계 | PM 또는 공통 작업 에이전트 |
| [작업기록_template.md](./작업기록_template.md) | 시작·종료·중단·통합 기록 양식 | 각 기록 작성자가 복사해서 사용 |

계획 파일은 **해야 할 일과 완료 기준**, 진행 파일은 **실제로 어디까지 했는지와 근거**를 관리한다. 팀 현황은 요약이며 상세 근거는 개인/PM 기록에 둔다.

## 2. 매 작업의 짧은 루틴

### 시작 — 계획과 마지막 상태 확인

1. `PM_plan.md → 진행현황.md → 이름_plan.md의 해당 Phase → 이름_progress.md의 최신 요약·마지막 기록` 순서로 읽는다.
2. 이번에 끝낼 작업 하나를 고르고 선행 조건·받아야 할 자료를 확인한다.
3. 진행 파일의 현재 작업을 `진행 중`으로 바꾸고, 읽은 계획·Phase·목표·완료 기준·검증 방법을 시작 기록으로 남긴다.

### 작업 중 — 의미 있는 결과가 생길 때 기록

- 구현한 기능, 확인한 실패, 기준 변경, 막힌 원인을 기록한다.
- 의존 작업이 필요하면 담당자·필요 결과물·그동안 할 수 있는 작업을 적는다.
- 네트워크/장비 시험 없이 추정한 상태는 확인 사실과 구분한다.

### 종료 — 기록·체크리스트·현황 맞추기

1. 누적 기록에 변경 파일, 확인 방법/실제 결과, 완료한 항목, 미검증·남은 일, 다음 행동, 인계를 적는다.
2. 완료 기준을 만족한 계획 체크박스만 체크한다. 부분 구현·검증 대기는 체크하지 않는다.
3. 개인 기록의 현재 요약과 Phase 표를 최신 상태로 바꾼다.
4. 팀 현황의 해당 사람 행을 맞춘다. 공유 파일 수정 시 최신 내용을 다시 읽고 다른 사람 행은 보존한다.
5. 다음 작업자가 처음 실행할 명령·열 파일·필요 장비 중 하나 이상을 구체적으로 남긴다.

## 3. 상태를 같은 의미로 사용하기

| 상태 | 의미 | 다음 행동 |
| --- | --- | --- |
| 확인 전 | 실제 착수·완료 근거를 아직 확인하지 않음 | 기존 작업과 증거를 먼저 확인 |
| 할 일 | 범위·기준은 정했지만 아직 시작하지 않음 | 선행 조건을 확인하고 착수 |
| 진행 중 | 구현·문서·측정 작업을 수행 중 | 결과와 검증을 남김 |
| 검토 요청 | 담당자 작업은 준비됐고 필요한 검토가 남음 | 검토자·확인 항목 명시 |
| 통합 확인 | 관련 모듈을 연결해 공통 기준을 확인 중 | 실제 통합 시나리오 수행 |
| 완료 | 해당 범위의 완료 기준과 필요한 검증을 충족 | 근거·완료일·인계 기록 |
| 막힘 | 필요한 자료·환경·결정이 없어 해당 작업이 멈춤 | 원인·도움 줄 사람·해제 조건 기록 |

- **개별 작업 완료:** 그 작업의 기준과 검증을 만족했다는 뜻이다. 다른 사람의 기능까지 완료됐다는 의미는 아니다.
- **개인 Phase 완료:** 그 사람에게 배정된 해당 Phase 작업과 필요한 인계를 확인했다는 뜻이다.
- **공통 Phase 완료:** `PM_plan.md`의 통합 기준을 확인하고 `PM_progress.md`에 확인자·결과·근거를 남긴 상태다. 팀원 모두의 추정 완료율로 대신하지 않는다.
- 새 실패나 설정 변경으로 기준을 충족하지 않으면 현재 상태를 다시 `진행 중`/`막힘` 등으로 바꾸고, 기존 완료 기록 뒤에 재확인 사유를 추가한다.
- 상태 판정에 필요한 검토 기록이 없으면 검토 중인 사실을 적고, 독립적으로 진행할 수 있는 다른 작업은 계속한다.

## 4. 기록 품질 기준

좋은 기록은 다음 질문에 답한다.

- 어떤 계획의 어느 Phase·체크리스트 항목을 수행했는가?
- 무엇이 바뀌었으며 어느 파일/PR/커밋에서 확인할 수 있는가?
- 어떤 조건에서 무엇을 확인했고 결과는 무엇인가?
- 실제 3대, 1대, 합성, 재생, 키보드 중 어떤 입력을 썼는가?
- 아직 안 된 것과 다음 한 단계는 무엇인가?

`카메라 완료` 대신 `C0 등록·좌우 손목 수신 확인, C1/C2 동시 수신은 미검증`처럼 적는다. 문서·에셋 작업은 `입력 출처: 해당 없음`, `검증: 문서 대조/에셋 로드`로 기록할 수 있다. 실행하지 않은 검증은 명령을 적더라도 `미실행`으로 표시한다.

## 5. 계획 변경과 동시 작업

- 범위·날짜·담당·인터페이스를 바꾸면 PM 기록에 이유·영향·새 기준을 적고 관련 계획을 함께 수정한다.
- 각자 자기 진행 파일을 중심으로 수정한다. 공유 현황은 변경 직전에 다시 읽고 자기 행 또는 공통 통합 행만 수정한다.
- 완료 체크를 취소해야 하면 과거 기록을 삭제하지 않고 원인과 재검증 대상을 추가한다.
- 현재 초기 상태는 `확인 전`이다. 기존 GitHub의 초기 서버·미리보기 설명과 팀원 각자의 실제 실행 확인을 구분한다.

## 6. Codex에서 사용할 요청 예시

작업 시작:

```text
이 프로젝트의 AGENTS.md와 PM_plan.md를 읽고, 김태이_plan.md 및
AGENTS/김태이_progress.md를 확인해 현재 Phase의 다음 작업을 진행해줘.
시작 기록을 남기고, 끝나면 검증 결과·남은 일·다음 작업을 파일에 갱신해줘.
```

마무리·인계:

```text
이번 작업의 실제 변경과 검증 결과를 담당자 progress 파일에 기록해줘.
완료한 계획 체크리스트만 체크하고, 개인 요약과 팀 진행현황을 맞춰줘.
아직 검증하지 않은 부분과 다음 재개 위치도 남겨줘.
```

## 7. 적용 범위

OpenAI Docs에 따르면 Codex는 실행을 시작할 때 프로젝트 경로의 `AGENTS.md`를 지침으로 읽는다. 그래서 루트 파일에서 이 폴더의 절차와 기록을 읽도록 연결했다. `AGENTS` 폴더 자체가 자동 실행 프로그램은 아니며, 사람과 에이전트가 따르는 작업 규칙과 기록 저장소다. [OpenAI 공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

이 기록 체계는 저장소 루트의 `AGENTS.md`, `AGENTS/`, 네 계획 파일을 함께 사용한다. 저장소를 clone하거나 main을 갱신한 뒤 [루트 README의 팀원 시작 안내](../README.md)를 따른다. 다른 위치로 복사할 때도 이 상대 경로 구조를 유지한다. 새 Codex 작업에서 적용 지침과 읽은 계획을 요약하게 하면 로딩 여부를 확인할 수 있다.
