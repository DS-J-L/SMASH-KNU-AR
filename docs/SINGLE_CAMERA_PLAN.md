# 휴대폰 카메라 1대 + PC 화면 플레이 계획

작성/고도화: 2026-11-03, Asia/Seoul. v0.2 설계를 보존하고 2026-11-06 로컬 구현을 반영했다. **main의 PC 소비자·손목/타격·소리 모듈과 로컬 방/서버를 연결해 두 방의 폰 좌표 2D 게임을 합성 검증했다. 실제 폰 통합·성능·3D는 미검증이다.** 기존 PC 추론 경로를 삭제하거나 main 게시 완료로 간주하지 않는다.

## 현재 실행 기준 — 2026-11-06

- 시험 경로는 [폰 좌표 게임](PHONE_POSE_GAME.md)이다. 방 2는 C0 한 대, 방 1은 C0/C1/C2 모두가 준비돼야 시작한다. C0 전송 방식은 서버 중계이며, 타격 계산에는 C0의 2D 손목만 사용한다.
- 폰의 한 스냅샷으로 관절 추론·JPEG를 만들고, 서버가 등록 관측과 대조해 정규화 손목을 영상에 묶는다. PC는 같은 프레임으로 표시·타격·파편/소리·100점·60초를 처리하고 서버가 점수/세션을 보관한다.
- 기본 방 페이지의 시작은 `video_check`다. 건물 게임은 해당 방의 ‘폰 좌표로 2D 게임 · C0 서버 중계’ 링크 → ‘휴대폰 연결 준비’ → ‘시작’ 순서다. `/monitor/single/`은 기존 PC 경로로 보존한다.
- 별도 `/ws/single/control`·동적 방 생성·서버 영구 로그는 미구현이다. 현재 room.v1을 기존 PC 소비자 DTO에 연결했으며 프로토콜 전체를 교체한 것이 아니다.
- 실폰/실제 모델·소리 청취·정량 지연·장시간·실측 보정·3D 타격이 남아 있다. 기존 SC 체크리스트의 실기기 완료 조건은 유지한다.

함께 볼 문서: [인터페이스·상태·단위](SINGLE_CAMERA_INTERFACES.md), [시험 ID·현장 실행표](SINGLE_CAMERA_TEST_PLAN.md), 개인 계획 [이동수](../이동수_plan.md)·[김태이](../김태이_plan.md)·[정경호](../정경호_plan.md). 본 문서와 두 상세 문서가 SC 추가 경로의 같은 v0.2 설계 묶음이다.

## 1. 권고하는 첫 결과물

휴대폰을 고정해 사용자 상체와 양손을 촬영한다. PC에는 그 영상 위에 IT 1호관 1개를 표시한다. 화면에서 손목을 휘둘러 건물 영역을 통과하면 기존 파편·점수·60초·복원을 연결한다.

| 모드 | 판정 기준 | 이번 계획의 범위 |
| --- | --- | --- |
| single_view_2d | 영상상의 손목 궤적과 건물의 화면 투영 영역 | 첫 구현 권고. 건물·파편 표현은 3D를 재사용 |
| multiview_3d | 보정된 공통 월드의 실제 3D 궤적 | 기존 3대 계획 유지. 최소 2개 유효 시점 등 기존 기준 유지 |
| 단안 3D 확장 | 인체/깊이 추정과 카메라 정합을 추가 검증 | 후속 실험. 이번 주 완료 조건에 포함하지 않음 |

단일 2D 모드는 화면 앞뒤 깊이가 달라도 겹치면 타격될 수 있다. 실제 실내 바닥의 m 좌표·깊이 판정 완료로 보고하지 않는다. MediaPipe의 WorldLandmarks는 골반 중심을 원점으로 한다. 따라서 이 값을 기존 room_z_up의 바닥 기준 손목 위치로 바로 쓰는 것은 적절하지 않다는 설계 판단이다. [MediaPipe 공식 출력 정의](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js)

기존 다중 모드의 1시점 거부·시간 정렬·보정 품질 검사를 완화하지 않는다. 다중 모드에서 카메라가 끊겨도 자동으로 2D 타격을 섞지 않는다. 모드 변경은 새 세션에서 수행하고 점수·궤적·이벤트 기록을 초기화한다.

## 2. 재사용할 것과 새로 만들 것

목표 게임 모듈과 현재 로컬 구현을 구분한다. 실행 계약은 [ROOMS.md](ROOMS.md)를 따른다.

| 구분 | 현재 근거 / 계획 |
| --- | --- |
| 손목 추출 | web/camera/pose.js의 로컬 모델·GPU/CPU 대체·15/16번 추출을 폰에서 재사용. 기존 PC PoseAdapter도 보존 |
| 건물·파편 | knu-it1-v3의 정상 모델·96개 파편·충돌체 우선 재사용. 본관/전체 캠퍼스는 첫 통합 후 확대 |
| 게임 | main의 frontend/game·single 게임/프레임·타격·물리/소리 모듈을 재사용 |
| 통신 | room.v1에 phone_2d 시작/상태·짝지어진 영상/좌표·game_hit를 연결. 기존 /ws/pose와 별도 PC ControlLink 초안은 구분 |
| 추가 연결 | 폰 스냅샷/관절·JPEG 짝, 정규화 손목 변환, 방별 입력/점수 격리, PC 소비자 어댑터·진입점 |

기존 키보드 데모와 카메라 중지/재시작 회귀 시험은 유지한다. 기존 데모 파일에 단일 모드 입력을 직접 덧붙여 테스트 입력과 실제 입력이 섞이게 하지 않는다.

## 3. 데이터 흐름: 현재 실행과 기존 PC 추론 설계

현재 phone_2d 실행 경로:

~~~mermaid
flowchart LR
  Phone["폰: 한 스냅샷으로 MediaPipe·JPEG"] --> Server["room.v1: 소유 관측 검증·정규화 손목 짝"]
  Server --> PC["PC: 같은 영상·손목 프레임 표시"]
  PC --> Hit["기존 2D 궤적 판정·파편·소리"]
  Hit --> Score["서버: 세션·중복 검사·100점 보관"]
~~~

아래는 2026-11-03 v0.2에서 제안한 별도 PC 추론 경로다. 해당 모듈·설계는 유지하며 현재 폰 좌표 게임의 실제 전송 방식과 혼용하지 않는다.

~~~mermaid
flowchart LR
  Phone["휴대폰: 카메라 촬영"] -->|WebRTC 영상| Receiver["PC: 영상 수신·프레임 확보"]
  Receiver --> Pose["PC: MediaPipe 손목 추출"]
  Receiver --> View["같은 프레임을 PC 배경에 표시"]
  Pose --> Hit["화면 2D 궤적 판정"]
  Hit --> Game["기존 3D 파편·점수·60초·복원"]
  Signal["FastAPI: 연결 신호·상태·로그"] -.-> Phone
  Signal -.-> Receiver
~~~

**v0.2의 최초 권고는 PC 추론이었다.** 폰 영상만 받아 PC 수신 프레임에서 추론·표시를 묶는 D01 예외 제안이었다. 2026-11-06 사용자 요청의 현재 시험 경로는 폰 추론+같은 스냅샷 JPEG로 연결했다. 이는 처리 위치 선택/로컬 연결 변경이며 실제 성능 우위를 측정한 결론은 아니다. 기존 3대 모드의 폰 추론·서버3D 책임은 유지한다.

- WebRTC는 영상을 전달하고 FastAPI는 SDP/ICE 등 연결 신호를 중계한다. WebRTC를 도입한다고 신호 교환·페어링 서버가 자동으로 생기지는 않는다. 방/기기/스트림 소유권을 정하고 기존 접속 보호 방식과 맞춘다. 엔드포인트·소유권·상태 기준안은 상세 인터페이스 문서에 적었으며 개발 PR에서 실제 스키마와 함께 검증한다. [WebRTC 연결 안내](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Signaling_and_video_calling)
- 폰 HTTPS·권한·렌즈/방향을 먼저 확인한다. 같은 Wi-Fi에서 우선 시험하되 학내 AP 격리·방화벽이면 개인 핫스폿으로 확인하고, 다른 망 접속이 필요하면 TURN 필요성을 검토한다. 기존 서버 외부 접속 성공 기록만으로 영상 경로까지 검증됐다고 판단하지 않는다. [카메라 보안 컨텍스트](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- PC에서는 한 번에 추론 1건만 실행하고 대기 프레임을 쌓지 않는다. 새 프레임의 스냅샷과 결과를 같은 frame_id로 묶고, 게임 배경에는 그 결과에 대응하는 프레임을 사용한다. 오래된 결과는 버린다.
- MediaPipe detectForVideo는 동기 실행이므로 렌더 부하를 함께 측정한다. Worker/OffscreenCanvas는 짧은 호환 시험 후 적용하고, 미지원이면 추론 빈도·해상도를 낮춘다. 폰 추론으로 바꾸는 대안은 영상/관절 정렬 비용까지 비교한 뒤 선택한다. [동기 추론과 Worker 안내](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js)
- WebRTC의 captureTime은 제공되지 않거나 추정값일 수 있다. PC 처리 시각으로 원래 촬영 시각을 만들어내지 않는다. 단일 모드의 입력 만료는 PC 수신/처리 시계로 관리하고, 전체 동작 지연은 별도 측정한다. [프레임 시각 메타데이터](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)

## 4. 화면 좌표·타격·게임 계약 제안

아래는 상세 인터페이스와 함께 사용할 구현 기준안이다. 개발 PR에서 양쪽 모듈을 대조한다. 현재 DATA_CONTRACT.md의 메시지 스키마를 이 문서만으로 변경하지 않는다.

1. 손목은 추론에 사용한 원본 프레임 픽셀 기준이다. 화면 표시에서는 letterbox·크롭·회전·거울 변환을 영상, 손목, 건물 충돌 영역에 동일하게 적용한다. 화면 크기나 영상 설정이 바뀌면 변환을 갱신하고 이전 궤적을 끊는다.
2. 직전/현재의 연속 유효 손목 사이 선분과 건물의 화면 충돌 영역을 검사한다. 단순 겹침 유지로 반복 타격하지 않으며, 신뢰도·움직임 기준·영역 진입/이탈·cooldown을 구분한다. 빈 공간은 타격 영역에서 제외한다.
3. 사람 미검출·화면 밖·낮은 신뢰도·오래된 프레임·연결 끊김이면 타격을 중단한다. 복구 첫 유효 점은 시작점만 저장해 가짜 긴 궤적을 만들지 않는다. 정지 화면을 새 입력으로 반복 추론하지 않는다.
4. 공용 이벤트에는 session_id, event_id, building_id, joint, tracking_mode=single_view_2d, task_type, source를 남긴다. 단일 모드에는 hit_point_image_norm와 speed_norm_per_s를 제안한다. 속도 단위는 원본 영상 대각선 길이/초다. hit_point_m·speed_mps는 null로 구분하고, 다중 3D 모드에서 필요한 m 좌표를 선택 사항으로 완화하지 않는다.
5. 3D 파편의 연출용 충격점은 가상 건물 표면에 매핑할 수 있으나 실제 측정한 공간 접촉점과 다른 값으로 기록한다. 2D 이벤트를 pose_3d의 valid=true로 포장하지 않는다.
6. 단일 게임 session_id는 PC GameController가 만들고 서버 ACK 후 시작하는 기준안으로 정리한다. room_id·stream_id·서버 추적 런타임 ID는 별개다. 재시작/중복 요청·복구 정책은 인터페이스 2절을 따른다. 종료 후·이전 세션·중복 이벤트는 점수에 반영하지 않는다.
7. 단일 모드 준비 조건은 선택한 C0 영상·새 프레임·유효 손목·표시 변환·장면 준비다. C1/C2·실측 3D 보정을 요구하지 않는 별도 조건을 만들되 기존 multiview_3d의 준비 조건과 글로벌 상태를 임의로 true로 만들지 않는다.
8. UI에 화면2D 판정과 준비 불가 이유를 표시한다. 유효 손목만 미검출이면 타격을 차단하고 시간은 흐른다. 현재 phone_2d는 필수 카메라 종료·영상/짝 좌표1.5초 중단 시 자동 중지한다. 실제 평가 전 모드별 정책과 근거를 고정한다.

## 10. 사용 흐름과 범위 축소 순서

PC에서 '1대 · 화면 2D 판정' 선택 → 폰 연결 정보 표시 → 폰 카메라 권한/렌즈 선택 → 영상·손목 미리보기와 건물 위치 확인 → 준비 사유가 모두 충족되면 시작 → 60초·점수·연결/추적 상태 표시 → 결과·재시작이다. 로딩·권한 거부·망 실패·모델 실패는 사용자가 다시 시도할 행동과 함께 표시한다. UI에 API/Worker 같은 내부 용어를 노출할 필요는 없다.

1. IT1 1개·카메라/건물 고정·contain·1인·양손부터 연결한다. 파편은 기존 96개를 우선 쓰되 성능 측정 결과로 활성 수를 조정하고 설정에 남긴다.
2. 지연이 크면 해상도/추론 빈도·효과/파편 활성 수를 순서대로 측정·조정한다. 입력 TTL을 늘려 과거 동작을 타격시키는 방법으로 통과하지 않는다.
3. 11/04 영상 미연결이면 김태이/정경호/이동수가 송신·ICE/망·수신 경계를 나눠 진단한다. 다른 작업자는 허용된 replay/합성으로 자기 모듈을 계속 검증한다.
4. 11/05 Worker/GPU 호환이 막히면 CPU·제한 빈도 경로를 비교한다. PC 추론이 목표를 못 맞추면 폰 추론 대안의 영상/관절 정렬을 별도 설계·측정한 뒤 계획을 수정한다.
5. 11/06 게임 연결이 미완료이면 11/07~08에는 장식/추가 건물보다 실패·복원·계약을 우선한다. 키보드/재생 시연은 모드와 출처를 분명히 표시한다.
6. 11/09 선행 연결·무효 입력 차단이 실패하면 점수/인식률 측정을 보류하고 원인·담당·재시험을 남긴다. 장비 시험 예약이 기능 완성을 보장하지 않는다.
